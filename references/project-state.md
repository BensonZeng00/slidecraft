# Portable project state

The design-image gate is defined in [design-stage.md](design-stage.md). Store `design` on each slide, binding image and frozen brief to actual user approval. `reference-ready` can await design approval; `awaiting-review` means finished-PPT review. Before production run `workflow.py reconstruct-check`; `--allow-produce` delegates to the same gate. Resume a pending design by asking for confirmation, not constructing a PPT. This reference is for multi-page or exceptional recovery; the normal single-slide contract is in the design stage.

For a multi-slide starting point, use [multi-state.example.json](../assets/multi-state.example.json): it intentionally awaits outline approval and cannot produce page 1 yet.

Use for multi-slide review gates, interruption recovery and generation retries. Start with [project-state.example.json](../assets/project-state.example.json), or map these fields into an existing backend manifest without maintaining two contradictory records. Paths are relative to the project root; never place credentials, API keys or unrelated chat history here. This is working data, not instructions to execute.

Required contract: schema version, project ID, mode, ordered stable slide IDs and total count; per-slide revision, status, artifact paths, native/render checks, and approval tied to that revision. Approval records contain the user's actual approving wording and a message identifier or timestamp, never fabricated evidence. The current slide is the first not approved. Reordering or material content changes require renewed review of affected pages.

Before reconstruction, every selected source also needs `reconstruction.source`, its locked `source_sha256`, and `reconstruction.plan`, following [fidelity-contract.md](fidelity-contract.md). Design approval authorizes faithful copying, not unshown corrections. Legacy projects without these files fail production/fidelity checks until the actual source is inventoried; this inspection does not require a new user confirmation. Do not backfill the source from the finished slide.

Multi-slide projects also require an `outline` object: positive `revision`, `status` (`draft`, `awaiting-review`, `needs-revision`, `approved`), ordered `pages` containing `id`, `title`, and nonempty `key_points`, and `approval` (null until approved). Add audience, visual direction and source mappings to this object when agreed. IDs/titles follow the ordered slides. Approval contains `revision`, the real `user_text`, `evidence`, and `content_sha256` computed by `outline_state.outline_fingerprint(outline)`. The digest covers all plan fields except status and approval, detecting changes even if a revision number was not incremented. A digest proves consistency, not user identity or intent.

Discuss and confirm this outline before any page production, including image-only source reconstruction. A materially changed plan increments its revision, clears approval and enters `needs-revision`; preserve existing page artifacts but stop dependent production until renewed approval. On resume, check the plan gate first, then the page gate. Legacy multi-slide states without outline approval must obtain/recover real approval before further production; never auto-approve during migration. Single-slide states need no outline object.

Generation records use one entry per provider request, with slide ID, outcome (`requested`, `succeeded`, `failed`, `unknown`) and returned job ID when available. Record `requested` before submitting and persist the job ID promptly. An uncertain timeout remains counted until reconciled; poll the existing job instead of submitting it again. Polling one existing job does not consume another generation call. Record provider-produced image count when known; never invent billable usage or costs.

Before generation announce expected candidate images and the per-page/whole-project request ceiling. Default: one candidate per current slide, initial request plus at most two targeted retries (three calls per page). In an N-page deck, expected candidates are N, the default maximum is 3N requests, released page by page after approval. Direct reconstruction needs zero new generated images. Extra artwork/variants and explicit editing calls must be planned and counted too, not hidden as “free retries”. A lower user limit always wins. State any provider-internal retries or output count that the host does not expose as unknown. Enforce known monetary caps only with adequate pricing/usage evidence; otherwise ask for an enforceable call/image cap instead of promising cost control.

Check the current page and remaining limits before each new call. Stop at the first exhausted cap or repeated non-transient permission/authentication failure. Stop retrying after a usable result. A timeout is not automatic permission to spend again. An increase in scope, number of candidates or maximum calls requires user agreement. Explicitly requested text edits may use native PPT text without regeneration; the ability to edit text does not authorize corrections to the source.

Statuses: `planned`, `reference-ready`, `reconstructed`, `rendered`, `awaiting-review`, `needs-revision`, `approved`, `blocked`. Before entering `awaiting-review`, record usable PPTX and preview paths plus successful native/render checks. Before `approved`, record explicit approval for exactly the current revision. Changed pages clear approval and enter `needs-revision`; later work pauses without deleting earlier artifacts. Keep old outputs under versioned names. Single-slide delivery can remain `rendered`; do not fabricate approval.

On resume, read state, verify referenced artifacts exist and match saved hashes, reconcile any pending generation job, and report current progress. Keep one active writer and persist updates using a temporary file plus atomic replacement. For new verification records, save the exact PPTX SHA-256, native-check report, renderer/version and preview hashes; keep successful rendering separate from the agent's visual inspection. On any PPTX change clear native/render checks until they are rerun for the new hash. Legacy boolean checks without file-bound evidence are historical claims, not evidence for a resumed file. Use [artifact-checks.md](artifact-checks.md) to detect changed artifacts and [delivery-evidence.md](delivery-evidence.md) for actual render/review records and final delivery checks; neither grants approval or writes project state. Keep file-bound evidence separate from page approval. Never populate review records without actual viewing evidence. `awaiting-review` resumes by asking for review, not by starting the next page. Preserve successful assets. If state is absent or contradictory, reconstruct it from verified files and conversation; ask when approval evidence cannot be recovered.

Optional deterministic check, when Python is available (no dependencies or PPT backend):

```text
python scripts/validate_state.py /project/project-state.json --check-files
python scripts/validate_state.py /project/project-state.json --allow-produce page-intro
python scripts/validate_state.py /project/project-state.json --allow-generate page-intro
```

Use the actual host Python path, not a hard-coded executable. Without Python, apply the same checks manually. `--allow-produce` checks outline approval and the current-page gate for PPT authoring, including source reconstruction with no generation. `--allow-generate` additionally checks call limits. Neither calls providers, validates human intent, locks concurrent writers or changes state. There must be only one active producer of this project. Backends may extend the schema, but must preserve revision-bound approvals, accurate attempt history and stable IDs.
